> AI 原生企业业务建模、运行与分析平台

## 2. 产品定位

Xanze 不是一个“加入 Agent 的 OA 系统”，而是一个 AI 原生的企业业务应用平台。

企业可以在 Xanze 中定义业务数据、字段关系、表单、流程、权限、Agent 和分析看板，
再将它们发布成可供员工直接使用的业务应用。

OA、CRM、ERP、HRM、项目管理、合同管理、风险管理等属于基于平台能力构建的
解决方案模板，而不是相互独立、重复建设的系统内核。

Xanze 的核心价值不是让 AI 生成更多页面，而是让 AI 在可治理的前提下理解并参与：

1. 业务结构设计；
2. 字段值计算、补全和关联；
3. 任务分派与业务流转；
4. 数据分析与经营看板生成；
5. 应用修改、测试、发布、审计和回滚。

## 3. 要解决的问题

传统低代码平台主要解决“页面和流程搭建速度”，但经常存在以下问题：

- 数据模型、表单、流程、报表彼此割裂；
- AI 只能生成文本，无法安全参与真实业务；
- 业务人员的自然语言需求难以稳定转换为可运行配置；
- 自动生成的数据缺少来源、置信度和审核记录；
- 修改线上流程风险高，缺少 Diff、验证、试运行和回滚；
- 从业务表格生成的看板只有视觉效果，没有可靠的指标口径；
- OA、CRM、ERP 等模块各自建设，数据和权限难以统一。

Xanze 通过统一业务语义模型、受控 Agent 运行时和版本化发布机制解决这些问题。

查看 AI 操作、敏感数据访问、配置变更、业务流转和发布回滚记录。

## 5. 产品形态

Xanze 包含两个逻辑入口，但共享同一身份、权限、数据和审计体系。

### 5.1 工作门户

面向企业员工，提供：

- 已发布业务应用；
- 我的待办和已办；
- 表单与业务记录；
- 通知和订阅；
- 数据看板；
- Agent 助手及其可执行操作。

员工只能看到其角色、组织、数据范围和字段权限允许访问的内容。

### 5.2 平台控制台

面向管理员和业务设计者，提供：

- 业务对象与关系建模；
- 动态表单和列表设计；
- 字段智能规则；
- 流程与 Agent 编排；
- 数据集与看板设计；
- 权限、版本、发布、审计和回滚。

## 6. 产品原则

### 6.1 模型驱动

应用的表单、列表、规则、流程和看板应由结构化模型驱动，不能依赖大量写死页面。

### 6.2 AI 产生提案，平台负责约束

AI 的输出必须经过结构化解析、权限检查、规则校验和审计，不能直接修改生产配置或数据库。

### 6.3 先可解释，再自动执行

所有 AI 生成的字段值、业务决策和分析指标都应能够追踪来源、依赖和执行过程。

### 6.4 设计态与运行态分离

草稿修改不得直接影响员工正在使用的应用。只有通过验证并发布的版本才能进入运行态。

### 6.5 权限贯穿全链路

页面权限、接口权限、数据范围、字段权限、Agent 工具权限和流程执行权限必须使用统一策略。

### 6.6 纵向闭环优先

每项能力必须完成数据库、服务端、前端、权限、审计和自动化测试的真实闭环，
不以空菜单、静态页面或 Mock 数据表示完成。

### 6.7 模板不是内核

OA、CRM、ERP、HRM 等业务套件通过平台模型和扩展机制实现，不在内核中重复建设专用引擎。

## 7. 统一业务语义模型

### 7.1 Application

一个可独立设计、发布和授权的业务应用，例如“工程项目风险管理”。

### 7.2 BusinessObject

企业中的一个业务实体，例如项目、合同、风险、客户、员工或审批单。

### 7.3 FieldDefinition

业务对象的字段定义，包括：

- 字段名称和稳定标识；
- 数据类型；
- 是否必填、唯一或只读；
- 默认值和校验规则；
- 展示格式；
- 敏感级别；
- 字段级读取和写入权限。

### 7.4 RelationDefinition

业务对象之间的一对一、一对多、多对一或多对多结构关系，并定义基数、引用、级联和删除策略。

### 7.5 RelationProposal

Agent 或数据分析器发现的候选关系。候选关系必须包含关系类型、来源、目标、证据、
置信度、样例、异常数据和预计影响，在人工确认前不能进入运行态。

### 7.6 SemanticRelation

字段、对象或数据集之间经过确认的业务语义关系，例如公式、查找、聚合、条件、
时间、层级、实体匹配和疑似因果关系。SemanticRelation 本身描述业务事实，
不等同于数据库外键，也不直接执行数据写入。

### 7.7 RecordRelation

两条具体业务记录之间的关系，例如“属于项目”“对应合同”“补充协议”“后续整改”
或“疑似重复”。每条关系都要记录来源、置信度、有效期和确认状态。

### 7.8 FormDefinition

业务对象的表单结构，包括分组、布局、字段组件、显示条件、交互规则和操作按钮。

### 7.9 ViewDefinition

业务对象的列表、详情、搜索、筛选、排序、聚合和批量操作配置。

### 7.10 Record

业务对象在运行态中的一条真实记录。记录的读取和修改必须经过业务模型及权限层。

### 7.11 ValueBinding

由已确认 SemanticRelation 编译而来的可执行字段绑定，定义目标字段、输入依赖、
触发条件、执行器、校验、写入方式、审批和失败策略。

### 7.12 CellLineage

记录一个具体单元格由谁、何时、根据哪些源单元格、关系版本、规则或模型产生，
以及置信度、输入摘要、人工覆盖和审核状态。CellLineage 是字段级血缘和审计的事实来源。

### 7.13 WorkflowDefinition

业务状态、节点、条件、任务、网关、事件、超时和补偿机制的版本化定义。

### 7.14 AgentDefinition 与 AgentBinding

AgentDefinition 描述 Agent 的能力和运行配置；AgentBinding 描述 Agent 在特定业务对象、
字段或流程节点中可以读取什么、调用什么、输出什么以及是否需要审批。

### 7.15 ReadOnlyDataset

通过文件快照、数据库只读账号或授权视图接入的数据集。平台可以分析、查询和生成衍生结果，
但不能修改源数据。每个数据集必须记录来源、快照、刷新时间、访问范围和敏感字段策略。

### 7.16 DataProfile

数据集的可重复画像，包括字段类型、唯一率、空值率、分布、异常值、候选主键、
候选外键、函数依赖、时间范围和数据质量问题。

### 7.17 DatasetSemanticModel

对只读数据源中的表、字段、关系、时间、维度、指标、敏感信息和数据质量进行语义描述。

### 7.18 MetricDefinition

经过确认的指标定义，包括名称、计算公式、聚合方式、单位、时间窗口、维度、
过滤条件、分母、排除项、数据来源和负责人。

### 7.19 DashboardSpec

可版本化的看板定义，包括数据集、指标、维度、筛选器、图表、布局、刷新策略和权限。

### 7.20 Policy

统一描述角色、组织、记录、字段、工具、Agent 和环境的访问及执行规则。

### 7.21 Draft、Release 与 AuditEvent

- Draft：可编辑但不影响运行态的设计版本；
- Release：通过验证并发布的不可变版本；
- AuditEvent：对模型、数据、流程、Agent 和发布操作的审计事件。

## 8. 五大平台能力

### 8.1 业务语义建模

用户可以通过可视化方式或自然语言定义：

- 业务对象和字段；
- 对象关系；
- 动态表单和列表；
- 字段依赖和计算规则；
- 权限和数据范围；
- 应用导航和工作门户入口。

### 8.2 业务应用运行

平台根据已发布模型动态提供：

- 表单填写与校验；
- 记录查询和修改；
- 状态变更；
- 任务和待办；
- 通知及事件；
- 权限判断和审计。

### 8.3 Agent 业务执行

Agent 不只回答问题，还可以在授权范围内：

- 读取业务上下文；
- 补全或建议字段值；
- 检查数据一致性；
- 调用企业工具；
- 创建任务或业务记录；
- 执行流程节点；
- 汇总执行结果并请求人工确认。

### 8.4 智能数据分析

平台可以在只读权限下：

- 分析数据表结构和数据质量；
- 识别候选维度、指标和时间字段；
- 建立经过确认的指标口径；
- 生成可编辑的 DashboardSpec；
- 渲染看板、筛选器和下钻路径；
- 解释异常并展示数据来源。

### 8.5 安全治理与发布

所有模型和 AI 变更都应支持：

- 结构化 Patch；
- 版本 Diff；
- Schema 和规则校验；
- 影响分析；
- Dry-run 或沙箱试运行；
- 人工审批；
- 分环境发布；
- 审计和回滚。

## 9. AI 语义关系与单元格智能

Xanze 的核心能力之一，是自动发现、建议、验证并建立字段、记录和具体单元格之间的业务关系。
关系不是由大模型凭名称猜测，而是由数据分析、业务知识和 Agent 联合形成并提供证据。

### 9.1 三层关系

字段级关系描述列与列之间的稳定语义，包括：

- `FORMULA`：计算关系；
- `LOOKUP`：关联对象取值；
- `FOREIGN_KEY`：候选或已确认的引用关系；
- `AGGREGATION`：明细到汇总；
- `CONDITION`：条件推导；
- `TEMPORAL`：时间先后、周期和逾期；
- `HIERARCHY`：组织、区域或分类层级；
- `ENTITY_MATCH`：同一实体识别；
- `CAUSAL_HINT`：仅作为待验证的影响假设；
- `AGENT_DERIVED`：由受控 Agent 推导。

记录级关系描述具体行之间的联系，例如付款属于合同、风险属于项目、
补充协议对应原合同、整改事项来源于风险或两条客户记录疑似重复。

单元格级关系描述一个具体值依赖哪些源单元格和规则版本，例如：

`Risk/R-102.riskScore <- probability * impact @ relation-v3`。

### 9.2 关系发现流程

标准发现链路为：

1. 读取 Schema、字段说明和经过权限裁剪的数据样本；
2. 生成 DataProfile；
3. 用确定性算法发现唯一性、函数依赖、公式匹配、相关性和候选外键；
4. Agent 结合业务词汇、数据字典和上下文解释候选关系；
5. 形成包含证据、置信度、匹配率、异常样本和预计影响的 RelationProposal；
6. 在历史数据或只读快照中回放验证；
7. 用户接受、修改或拒绝；
8. 接受后生成版本化 SemanticRelation；
9. 可执行关系被编译为 ValueBinding；
10. 发布后持续监测关系失效和数据漂移。

没有配置模型提供方时，平台可以执行确定性画像和关系发现，但必须明确显示
“AI 语义解释不可用”，不得用模板文本或随机结果冒充真实 Agent。

### 9.3 RelationProposal 最小信息

每个候选关系至少包含：

- `relationType`：关系类型；
- `sourceRefs`：源字段、记录或数据集；
- `targetRef`：目标字段、记录或指标；
- `expression`：可选的表达式或匹配规则；
- `evidence`：统计证据和示例；
- `confidence`：置信度；
- `exceptions`：不符合关系的异常数据；
- `impact`：接受后影响的字段和记录数量；
- `suggestedAction`：接受、修改、补充数据或拒绝建议；
- `status`：建议、已确认、已拒绝、已发布或已失效。

### 9.4 ValueBinding

Xanze 不允许 Agent 绕过业务服务随意修改数据库单元格。
写入或计算字段必须通过 ValueBinding。ValueBinding 至少包含：

- `targetField`：目标字段；
- `dependencies`：依赖字段、关联对象或数据集；
- `sourceType`：人工、默认值、公式、查找、受控查询或 Agent；
- `trigger`：触发时机；
- `condition`：执行条件；
- `executor`：沙箱公式、受控查询、规则或 Agent；
- `writeMode`：建议、自动写入或审批后写入；
- `validation`：类型和业务校验；
- `confidenceThreshold`：最低置信度；
- `fallback`：失败或低置信度时的处理；
- `permission`：可查看、运行、确认和覆盖的主体。

### 9.5 CellLineage

每次非人工字段值产生或人工覆盖，都要形成 CellLineage，至少记录：

- 目标单元格；
- 源单元格或数据引用；
- SemanticRelation 和 ValueBinding 版本；
- 输入摘要及输出值；
- 规则、Agent、模型和提示版本；
- 置信度；
- 执行身份和时间；
- 审核状态和审核人；
- 修改前后的值。

关系规则保存在元数据层，不为每个普通单元格重复保存一份规则。
只对实际计算、AI 生成、跨表查询、人工覆盖和关键业务字段保存运行血缘。

### 9.6 关系运行安全

- 发布前必须执行类型检查和循环依赖检测；
- 关系图必须形成可执行有向无环图，特殊递归场景需要显式迭代上限；
- 公式只能在沙箱中运行；
- 依赖变化后只增量重算受影响子图；
- 关系版本变更前必须展示影响范围；
- 低置信度、冲突或高风险结果必须转人工；
- `CAUSAL_HINT` 不得自动升级为因果结论或执行规则；
- Agent 和分析服务不能直接写业务库。

### 9.7 四种工作模式

- `DISCOVER`：扫描现有表格并发现候选关系；
- `DESIGN`：根据自然语言创建或修改关系；
- `RUN`：按已发布关系计算字段和记录连接；
- `REPAIR`：发现失效关系、异常值和断裂引用并提出修复建议。

## 10. AI 工作模式

Xanze 将 AI 能力划分为不同权限等级，不能使用一个无限权限的通用 Agent。

### 10.1 DESIGN

根据自然语言提出业务模型、表单、字段关系、流程或看板的结构化变更。

### 10.2 ASSIST

解释当前业务、发现问题、提供建议，但不写入业务数据。

### 10.3 AUTOFILL

为指定字段生成建议值，默认需要用户确认。

### 10.4 EXECUTE

在明确的 AgentBinding、工具白名单和审批策略下执行真实业务操作。

### 10.5 ANALYZE

在只读数据权限下生成分析、指标建议、图表和异常解释。

每种模式都必须有独立的数据范围、字段范围、工具权限、执行预算和审计策略。

## 11. 自然语言修改协议

自然语言不能直接成为生产配置。标准变更链路为：

1. 接收用户意图；
2. 获取当前版本、权限和业务上下文；
3. 生成结构化 Patch；
4. 执行 Schema、权限和规则校验；
5. 生成 Diff 和影响分析；
6. 在沙箱中试运行或回放测试案例；
7. 展示风险、迁移方案和回滚点；
8. 获得有权限用户确认；
9. 生成新版本；
10. 发布并记录审计事件；
11. 支持回滚到上一个可用版本。

低风险、可逆操作可以按策略自动批准；高风险、跨对象、涉及敏感字段或生产流程的操作必须人工审批。

## 12. 流程与业务流转

流程不仅是可视化节点图，还必须拥有可执行语义。

流程节点可包括：

- 开始与结束；
- 人工任务；
- Agent 任务；
- 服务任务；
- 条件和并行网关；
- 子流程；
- 定时器和超时；
- 消息及业务事件；
- 人工审批；
- 补偿和异常处理。

Agent 节点必须声明输入、输出、可用工具、数据权限、超时、重试、幂等键、失败策略和人工接管方式。

## 13. 智能看板

“AI 读取表格并生成科技感看板”是 Xanze 的核心能力，但必须建立在只读隔离、
可靠语义、明确指标和可追溯查询之上。

智能看板与 AI 语义关系构建是两个独立功能。智能看板可以读取已经发布的
SemanticRelation 作为分析上下文，但不能创建、修改或发布 RelationProposal、
SemanticRelation、RecordRelation 和 ValueBinding；语义关系引擎也不负责生成图表。

标准链路为：

1. 通过不可变文件快照、数据库只读账号或授权视图获得 ReadOnlyDataset；
2. 识别表结构、字段类型、空值、重复值、异常值和敏感数据；
3. 生成 DataProfile，并读取已有且有权限访问的语义模型；
4. 看板 Agent 提出维度、指标、时间字段、筛选器和图表建议；
5. 用户确认指标名称、公式、单位、窗口、分母和排除项；
6. 生成版本化 DatasetSemanticModel、MetricDefinition 和 DashboardSpec；
7. 在只读查询沙箱中验证每个指标和图表数据；
8. 生成 KPI、趋势、分类比较、分布、明细表、筛选器和下钻；
9. 用户调整布局、主题和组件后发布到有权限的工作门户；
10. 看板展示刷新时间、指标定义、数据来源、查询血缘和数据质量提示。

DashboardSpec 必须是结构化、可编辑、可验证的配置，不能让模型生成任意前端代码。
第一版至少支持 KPI、折线图、柱状图、饼图和明细表，统一使用设计令牌形成科技感主题。

只读安全要求：

- 文件导入只读取值，不执行宏、公式脚本或嵌入内容；
- 数据库连接必须使用独立只读账号；
- 查询层只允许经过解析和验证的 `SELECT`；
- 强制行数、执行时间、并发和资源上限；
- 查询前应用租户、行级、列级和脱敏策略；
- 模型只能接收权限允许且经过裁剪或脱敏的数据样本；
- 看板不能提供写回源表的操作；
- 所有指标查询都要记录数据集版本、语义模型版本和查询血缘。

AI 不得虚构指标含义，不得把字段相关性描述成已证明的因果关系。
无法确认的指标必须保持“候选”状态，并要求有权限用户确认后才能发布。

## 14. 权限、安全与审计

平台至少需要统一支持：

- 租户隔离；
- 用户、组织、岗位和角色；
- 菜单及操作权限；
- 行级数据范围；
- 字段级读写权限；
- 敏感字段脱敏；
- Agent 工具白名单；
- 数据源只读策略；
- 生产发布审批；
- 密钥集中管理；
- 全链路审计；
- AI 输入输出的安全过滤和必要脱敏。

Agent 使用发起人的受限身份或明确的服务身份执行，不能默认继承平台管理员权限。

## 15. 版本、发布与环境

- 所有应用模型必须版本化；
- 草稿修改不得影响当前 Release；
- Release 发布后不可原地修改；
- 数据模型变更必须包含迁移和兼容性检查；
- 发布前必须通过自动化验证；
- 系统应支持开发、测试和生产环境；
- 发布失败不得破坏当前可用版本；
- 回滚行为必须被审计。

## 16. 首个示范场景

首个完整示范场景为“工程项目风险管理”，用于证明平台核心能力，而不是作为专用硬编码模块。

示范应逐步覆盖：

1. 项目与风险业务对象；
2. 动态表单和列表；
3. 风险分值公式；
4. 根据项目关联责任部门；
5. AI 提取风险描述并建议风险等级；
6. 风险处置流程和 Agent 节点；
7. 风险数据智能看板；
8. 字段来源、权限、审计、版本和回滚。

## 17. 解决方案模板

在平台内核稳定后，可以提供：

- OA：请假、用印、发文、会议、审批；
- CRM：客户、商机、跟进、合同；
- ERP：采购、库存、供应商、成本；
- HRM：员工、组织、考勤、绩效；
- 工程管理：项目、合同、风险、质量、安全、整改；
- 数据治理：数据质量问题、责任分派和整改闭环。

模板必须使用统一业务对象、流程、权限、Agent 和看板能力构建，不得形成独立技术栈。

## 18. 非目标

当前产品不以以下事项为目标：

- 一次性复制并重写所有 OA、CRM、ERP、HRM 功能；
- 将四个参考项目整体拼接成一个仓库；
- 用聊天界面替代业务建模和权限治理；
- 让大模型直接执行任意 SQL 或修改生产数据库；
- 用静态页面、Mock 接口或写死数据冒充动态应用；
- 追求节点数量、菜单数量或页面数量；
- 在核心闭环完成前建设大量边缘功能。

## 19. 参考项目的吸收边界

Xanze 可以吸收参考项目的设计思想，但必须形成统一原创架构：

- JeecgBoot：借鉴模型驱动、动态表单、数据字典和报表设计经验；
- Coze Studio：借鉴可视化编排、节点配置、调试和运行追踪体验；
- RuoYi：借鉴企业身份、组织、权限、审计和后台管理完整性；
- Yenz：借鉴结构化 Patch、Diff、影响分析、试运行、审批、版本和回滚机制。

不得整体复制任何项目的代码、菜单或视觉外壳。复用代码时必须核查许可证并记录第三方声明。

## 20. 分阶段路线

### 阶段 1：企业基础底座

完成可运行的身份、组织、角色、权限、门户、审计基础和容器化开发环境。

### 阶段 2：AI 语义关系构建器

完成 ReadOnlyDataset、DataProfile、RelationProposal、SemanticRelation 和 RecordRelation
的真实纵向闭环。用户可以导入工程风险台账的只读快照，查看列关系、记录关系、
统计证据和异常样本，确认后将关系写入 Xanze 的版本化关系模型。

阶段 2A 先完成安全导入、画像、确定性关系发现、关系确认和版本发布；
阶段 2B 再接入真实模型提供方，为候选关系增加业务语义解释和自然语言关系设计。
阶段 2 不生成看板，不建设动态表单，也不写回源表。

### 阶段 3：AI 只读表格看板

完成独立的 DatasetSemanticModel、MetricDefinition 和 DashboardSpec 纵向闭环。
看板 Agent 只读数据和已确认语义，提出指标与图表，用户确认后发布科技感看板。
阶段 3 不创建或修改关系，不写回源表。

### 阶段 4：业务对象、智能表单与字段运行时

完成 BusinessObject、FieldDefinition、RelationDefinition、FormDefinition、ViewDefinition、
Record、ValueBinding、CellLineage、Draft 和 Release，并复用阶段 2 的语义关系引擎。
随后完成自然语言到结构化 Patch、Diff、校验、试运行和可追踪的 Agent 字段补全。

### 阶段 5：流程与业务运行

完成流程定义、任务、网关、状态、事件、超时、Agent 节点和人工接管。

### 阶段 6：外部数据源与跨应用分析

将阶段 2、阶段 3 的文件快照能力扩展到数据库只读连接、授权视图、定时刷新、
跨对象指标和业务应用运行数据分析。

### 阶段 7：可视化 Agent 编排

完成面向企业业务对象、流程和工具的 Agent 画布、调试、追踪和评测。

### 阶段 8：解决方案模板与试点

基于统一平台构建工程管理、OA、CRM、ERP、HRM 等模板，并选择真实部门进行受控试点。

任何阶段未通过自身验收和前序阶段回归测试，不得宣布完成或进入下一阶段。

## 21. 产品级验收标准

Xanze 达到可试点状态时，至少应证明：

1. 管理员可以从模型创建一个业务应用并发布；
2. 员工可以在工作门户使用已发布应用；
3. 表单、列表和权限来自发布模型，而不是写死页面；
4. 只读表格可以生成可复现的 DataProfile 和带证据的 RelationProposal；
5. 用户确认后才能将候选关系和指标发布为正式版本；
6. 字段值可以由人工、公式、关联查询或 Agent 产生；
7. 非人工值具有完整 CellLineage；
8. 自然语言修改会产生 Patch、Diff、验证和新版本；
9. Agent 只能访问授权字段和工具；
10. 流程可以真实创建并推进人工及 Agent 任务；
11. 只读数据可以生成有明确指标口径、查询血缘和权限控制的看板；
12. 看板和 Agent 均不能写回只读源表；
13. 草稿不影响运行态，发布失败不破坏当前版本；
14. 未授权的页面、接口、记录和字段访问均被拒绝；
15. 关键路径拥有自动化测试、审计记录和可重复验收脚本。

## 22. 成功衡量

产品应持续衡量：

- 从需求到可运行应用的时间；
- AI 结构化变更一次验证通过率；
- AI 字段建议采纳率和人工修改率；
- 关系建议采纳率、误报率和历史数据匹配率；
- 自动生成字段的来源记录完整率；
- 流程自动化率和人工接管率；
- 看板指标口径确认率和查询血缘完整率；
- 越权访问和未审计写入次数；
- 发布失败率和回滚恢复时间；
- 真实业务用户的任务处理效率。

任何效率指标都不能以降低数据安全、业务正确性和可审计性为代价。
